## 坑 17：给控件设了 preferredSize 高度却不生效（v1.5.5）

**现象**：v1.1.1 起「调试输出区」就写着 `pal.debugBox.preferredSize = [320, 110];`，
但调试内容一多，面板照样被撑高 —— 那个 `110` 形同虚设，直到 v1.5.5 才被发现。

**根因**：紧随其后调用的 `pinW()` 内部有 `ctrl.preferredSize = [w, -1]`（**-1 = 高度自适应**）——
**在它之前设的高度被静默覆盖**。`pinW` 是三处一起钉（preferredSize / minimumSize / maximumSize），
本来只为「钉宽度」设计，却顺带把高度重置了。没有任何报错，只是"看起来没生效"。

**修法**：**先 `pinW` 钉宽度，再单独钉高度**。抽成 `fixedBox(parent, w, rows, text, readonly)`：
建控件 → `pinW` → 把 preferredSize / minimumSize / maximumSize 的**高度**都设成 `rows × LINE_H`，
配合 `{ multiline: true, scrollable: true }` ⇒ 超出部分走右侧滚动条，面板总高恒定。

**验证**：源码级**顺序体检**断言 —— `pinW(box, w)` 的位置下标必须小于 `box.preferredSize = [w, h]`；
并做**反向对照**：把两条对调立刻变红。

> **通用做法：`pinW` 之后再设高度。顺序反了不会报错，只会"看起来没生效"。**

## 坑 16：AE 报「在行 N 无法执行脚本」，而那一行是干净代码（v1.5.4）

**现象**：AE 弹「在行 2069 无法执行脚本。应为:」，并伴随「当模式对话框正在等待回应时，无法运行脚本」。
同一症状在 v1.1.2 时代出现过（当时报「行 1871」，两处指向**同一段代码**）。

**根因（实测时间线，非推测）**：

| 时刻 | 事件 |
|---|---|
| 08:52 | 提交 `6af45cb`（v1.2.0→v1.5.3 六版合入 main）—— 它第 2069 行 = `for (i = 0; i < SLOT_COUNT; i++) {` |
| **09:05:52** | **AE 进程启动**（`GetProcessTimes` 实测），载入当时磁盘上的脚本 |
| 09:38:59 | 部署 v1.5.3（= `6af45cb` + 版本号修正 2 行），**AE 未重启** |

ScriptUI Panel 脚本是 **AE 启动时**扫描载入的。磁盘文件后来被覆盖，AE 内存里仍是旧版 ——
于是它报的是**旧文件**的行号，与磁盘上的代码无关。这也解释了为什么「报错行随版本漂移，
但当前文件怎么编译都通过」。

**修法**：
1. 先证伪「当前文件有 bug」：`node --check` + **Rhino ES3 编译** + 不可见字符扫描（三档全过 = 文件没问题）
2. 比对 **AE 进程启动时间 vs 脚本文件 mtime** —— 前者更早就是没重启
3. 让用户**完全退出 AE**（关面板 / 关工程都无效）再开
4. **把版本号做进面板 UI**（v1.5.4）—— 打开面板即可判断 AE 里跑的是哪一版

**验证**：v1.5.4 面板顶部常驻 `v1.5.4` 标签；断言 261 全绿（含「顶部版本标签必须引用 VER 常量」的
源码级体检，已做反向对照：改成硬编码立刻变红）。

> **通用做法：AE 面板类 bug 先排除「AE 没重启」，再怀疑代码；报错行号要拿 git 历史反查版本。**
> 可复用的排查命令见 skill `ae-script-deploy` 的「诊断」一节。

## 12. 面板「边缘高度%」默认值下调，单改它会更糟（v0.9.0 附带）

**现象**：把「边缘高度%」默认值从 30% 降到 10% 时，需要同时改公式 —— 否则更看不见边缘。

**根因**：旧公式 `柱高 = max(峰高 × 衰减, 基础高度)`。要看见窗口边缘必须 `峰高 × e > 基础高度`。
e=30% 时门槛是 `峰高 > 基础高度 × 3.33`；**e 降到 10% 后门槛涨到 10 倍** —— 单降默认值反而更糟。

**修法**：两个改动**必须成对**。新公式下 e 的含义从"峰高的百分比"变成"**地板之上可用高度的百分比**"，
10% 已足够可见。

**验证**：实测同样参数在新旧公式下的"范围内最低柱高 vs 地板"（旧公式全部 0 超出）。

## 11. 「范围内的柱子起不来，必须要高度足够高」（v0.9.0）

**现象**：用户报「左右控制了之后只是影响范围，但是无法让最低的上去，必须要高度足够高，
这样的可控度还不够太够」。

**根因**：旧公式 `柱高 = max(峰高 × 衰减, 基础高度)` —— 边缘贡献低于基础高度时被**钳平**，
与范围外毫无差别。量化：要看见窗口边缘必须 **`峰高 > 基础高度 ÷ e`**，
默认 e=30% 时是基础高度的 **3.33 倍**。实测峰高 237.6 + 地板 150 → 边缘贡献 71.3 被钳到 150。

**修法**：把衰减作用在**地板之上**的区间：

```
柱高 = 基础高度 + (峰高 − 基础高度) × 衰减
```

- `pointContribution` 加 `baseH` 参数，返回"**超出地板多少**"而非绝对高度
- `combineHeights` 从 `max(合成, 地板)` 改成 **`地板 + 合成`**
- 表达式同步：`eff = pk - baseH; if (eff > 0) { v = eff * f; }` + 收尾 `h = baseH + h;`
- `baseH` 未给或为 0 → `effH = peak`，**与旧公式逐点相同**（旧调用零改动）

**连带发现**：`countVisibleBars` 旧版给下层传 `baseH=0`、再自己判 `h > baseH` ——
那是在**躲 `combineHeights` 的 max 钳制**。新公式下传 0 会让贡献退化成"从零起算"，
边缘又被判不可见（实测可见根数 9 → 7）。已改成把 `baseH` 真实传下去。

**验证**：7 组 (峰高, 地板) 组合下"窗口内最低仍高于地板" + "峰顶仍精确 = 峰高"；
反向对照 6/6 会变红。**探针踩过一次坑**：用"边缘可见性"去验证"是否减去 baseH"抓不到 ——
地板是加法基线，真正的破坏是**峰顶被抬高**。

## 10. 一个波峰要 3 个控制点，且边缘点不能被数成峰（v0.8.0）

**现象**：用户要「每个点控制的边缘也用两个控制点来确定」，并明确「一个波峰的控制点会有 3 个一组，
多个控制点就有多个组」。

**根因/设计**：新增空对象 `山峰点 k 左` / `山峰点 k 右`，拖它们的 X 定左右边界。
但**命名不能随意** —— 若新名字也以 `山峰点 ` 开头，"数点位"的逻辑可能把它们误算成峰。

**修法**：确认复用前缀**是安全的**，三条依据：

1. `countPoints` 用 `parseInt(nm.substring(PT_PREFIX.length))` 取编号，
   而 **`parseInt("1 左") === 1`**（parseInt 遇非数字即停）
2. `findLayer` 是**精确匹配**，不会命中 `山峰点 1 左`
3. `cleanup` 用 `indexOf(PT_PREFIX) === 0` ⇒ 边缘点**自动跟着被清理**

代码侧：`resolvePoints` 认 `points[].xl / .xr` → 输出 `{ r: 右半径, rl: 左半径 }`；
`pointContribution` 加**可选**参数 `rLeftPx`（不传 → 两侧同用 `rPx`，完全向后兼容）。

**验证**：三条命名安全性都写成断言；实测拖左边缘 → 左覆盖 5→14 而**右覆盖恒为 5**。

**交互配套**：`syncEdgeX` 是共用重摆函数 —— 「影响范围」字段变更 与 「重设点位」都要调用它，
否则边缘点会与峰错位，而且**「影响范围」会被边缘点架空，看着像个假参数**。

## 9. 想加"总闸"参数，差点撕毁旧契约（v0.7.0）

**现象**：用户要「增加一个控制高度的控制点，这个点位多高，最高高度就是多少」。
第一版打算把 `pointContribution` 的判据从 `hExplicit > 0` 改成 `>= 0`。

**根因**：`h = 0` 是「高度」滑块的默认值，表示"自动"。改成 `>= 0` 后 `0` 会变成"峰高 0" ——
**契约被撕成两半**，几十条既有断言 + 用户手上的旧工程一起炸。

**修法**：把归一化后的峰高**编码进 `y`**（`y = baseY − 峰高×s`），同时把 `h` 置 `-1`。
这样 `pointContribution` 走它原有的"自动"分支就得到正确结果 —— **判据一个字没改，既有断言零改动**。

**验证**：新增 71 条断言全绿，且既有 979 条**无一条改动**。

> **通用做法：加参数 / 加字段，不要改判据。判据是契约，参数是扩展。**

## 8. 参数做在「效果控件」里，面板上一个都看不到（v0.6.1）

**现象**：用户报「ui 上没有控制高度的参数呢。不是新增了参数控制吗，都没看到」。

**根因**：**我的设计错。** v0.4.1 的「高度」和 v0.6.0 的「边缘高度%」都只做成了
**图层效果控件**里的滑块（分别在 `山峰点 n` 和 `山峰 控制` 上），**面板上一个入口都没有**。
用户看的是面板，当然什么都看不到。

**修法**：两个参数都进面板「高度」区，且**改完立即生效**：
- `点位高度` onChange → `pushPointHeight()` 推给所有已有点位
- `边缘高度%` onChange → `pushEdgeToController()` 写控制器；老工程没有该滑块时**顺手补建**

**验证**：面板有对应输入框 + onChange 绑定的源码级断言。

> **教训：参数做在哪一层，用户就只会在哪一层找。面板才是操作台 ——
> 「效果控件里也能改」不算交付。**

## 7. kNN 半径差一个浮点尾数，填 9 只得 8 根（v0.5.0）

**现象**：把半径公式从 `(m+1)/2 × 柱距` 改成"第 m 近那根柱子的实际距离"（kNN）后，
填 9 实测只得到 8 根。

**根因**：`k×柱距` 常算出 `150.49999999999997`，而"第 m 近"那根柱子恰好落在 `150.5` ——
判定 `|d| ≤ R` 时被**挤掉**。

**修法**：半径末尾乘 `(1 + 1e-9)`。放大 1e-9 不影响任何实际像素位置。

**验证**：实测填 1~21 每一档都**恰好得到相同根数**。

> 这个数字是调出来的，不是随手加的 —— 注释里留了说明。

## 6. "填 9 却只看见 7 根"：可见根数跳号（v0.4.1）

**现象**：用户连着三轮都调不出想要的根数，报「影响范围填 9，一个点最多影响 7 个」。

**根因**：贡献 = `峰高 × 衰减(t)`。判定"这根动了吗"用的是"衰减 × 峰高 > 基础高度"。
余弦曲线衰减到 `基础高度/峰高` 以下时柱子被钳平 —— 默认值下这个门槛在 **t = 0.731**，
即只有半径的 **73% 视觉有效**。

更致命的是**可见根数跳号**：6 填到可见 5、13 填到可见 10，
**可见 7 / 9 / 13 / 15 / 17 这些值根本取不到**（满足门槛的柱子集合在对称窗口下先天跳号）。

**修法（当时）**：求衰减值时把 `t` 压缩到 `[0, FALL_EDGE]`，窗口边缘不再是 0。
**但这条在 v0.9.0 被更彻底的方案取代了**（见第 11 条）—— 现在的做法是"衰减作用在地板之上"。

**验证**：修复前后可见根数对照表（每档从"少 2 根"变成"一根不丢"）。

## 5. `File.saveDialog` 的第 3 个参数是我编的（v0.4.0）

**现象**：上一版为了让导出对话框"默认到工程目录"，给 `File.saveDialog()` 传了第 3 个参数（完整路径），
并声称"系统对话框会以它所在目录为起始目录"。

**根因**：**没有依据。** 查官方文档（extendscript.docsforadobe.dev · File Object）：

> `File.saveDialog(prompt[, preset=""])` —— **签名里只有两个参数，没有目录参数。**

而正确做法在同一页文档里：

> `fileObj.saveDlg(...)` —— *"Differs from the class method saveDialog() in that it
> **presets the current folder to this File object's parent folder**"*

**修法**：造一个 `File` 对象、调**实例方法** `saveDlg()` / `openDlg()`。
顺带推翻同一轮的另一句错话 —— 我说过"`openDialog` 没有目录参数、导入绕不过去"，
**也是错的**：`openDlg()` 一样能把起始目录设到工程目录。

**验证**：源码级断言 —— 出现 3 参 `saveDialog` 就变红。

> **教训：凡是"我记得 API 是这样"的写法，先去官方文档核一遍。**

同轮还修了：`randMath` 用 `Math.random()` 生成要 `setValue` 的值（官方建议 `generateRandomNumber()`）、
`pinW` 读回 `preferredSize.height` 再写回（首次布局前 volatile，会钉成 0）。

## 4. 点数 = 1 时「控制点完全没效果」（v0.3.3）

**现象**：用户报「点数改成 1，那个控制点没效果」，紧接着补充**「点数改成 2 是有效果的」**。

**根因**：这条补充把范围锁死了 —— **M=2 有效说明表达式链路是通的**，问题出在 M=1 这个特例上。
查出**两个**真因，都被 M=1 同时踩中：

1. **自动影响范围没封顶**：点数=1、40 根柱子时算出的半径是 **1700px**，而半行宽只有 675px
   → 整行都落在半径内、全被抬到接近峰高 → 看着就是"点在不在都一样"。
   M=2 时算 32 格，而且两点叠加本身有起伏，所以能看出效果。
2. **面板的「影响范围」只给新建点位设初值**：点数=1 时**没有新点被建**，所以怎么改都没反应；
   点数=2 时新建了点 2 拿到新值 → "有效果"。

**修法**：① `autoInfluenceBars` **封顶到 `N/2`**；② 「重设点数」→「重设点位」，
把面板的影响范围**统一推给所有已有点位**，并把 X 按新点数重新均分（Y 保留用户调好的值）。

**验证**：784 断言（+8），含"封顶边界"与"封顶后半行处贡献 < 5%"；反向对照验证封顶确实消除了"整行被抬平"。

## 3. 点「使用」回填预设，面板会弹宽（v0.3.2）

**现象**：用户报「使用预设的时候，ui 显示框会弹宽，很奇怪」。

**根因**：**两个因素叠加**。

1. **ScriptUI 的自动宽度**：`edittext` 和多行 `statictext` 一旦被赋 `.text`，
   **首选宽度会跟着内容重新计算**（`characters` 只给初值，压不住后续赋值）
2. 我在 `setStatus` 里多调了 **`pal.layout.resize()`** —— 它按当前首选宽度重排面板

「使用」这个动作**恰好同时踩中两步**：成批写 7 个输入框的 `.text` + 刷状态栏。

> 仓库里 `NumCounter` 和虚线网格**也都有 `layout.resize()`**，它们没暴露这个问题，
> 是因为它们没有"一次性回填一整面板控件"的交互。

**修法**：① 新增 `numBox()`，把宽度钉到 `preferredSize` / `minimumSize` / **`maximumSize`** 三处
（`maximumSize` 是硬上限，内容再长也只在框内滚动）；② 提示与状态栏一起钉宽；
③ **去掉 `layout.resize()`**；④ 导出提示不再打印完整路径。

**验证**：`grep -n "layout\.resize"` 确认**只剩注释、真实调用为 0**（不能靠感觉说改完了）。

## 2. 拖动形状图层，整行纹丝不动（v0.1.2）

**现象**：用户报「现在拖动集合图层，无法移动呢」。

**根因**：位置表达式里写了 `bx - transform.position[0]`，而 `bx` 又是从**控制器**的合成坐标推出来的 ——
两边一减，**图层自身的位置被完全抵消掉**：

```
合成X = 图层X + (bx − 图层X) = bx     ← 与图层位置完全无关
```

我当时把"行锚定在控制器上"当成设计特性，但这违背 AE 用户的直觉：**形状图层拖不动就是坏了**。

**修法**：**形状图层自己就是锚点**。`bx = transform.position[0] + …`、
`pk = transform.position[1] - pp[1]`、位置表达式输出**纯偏移量** `[(i-(N-1)/2)*(W+G), -h/2]`。

**验证**：新增"形状图层可拖动"回归节 —— 图层右移 200 → 合成坐标同步右移 200。
**测试当场抓到漏改的第三处**（`pk = cp[1] - pp[1]` 还在引用已删除的 `cp`，会直接 ReferenceError）。

## 1. 工具级事故：并行下发多个 Edit 会互相覆盖

**现象**：同一条消息里并行下发 11 个 `Edit`，实测**丢了 6 处**，
而工具**逐条回报 "Successfully edited"**。症状是 `resetSlots` 被引用却没定义（`ReferenceError`）。

**根因**：并行写同一个文件时发生写入竞争，后一次写入覆盖前一次。

**修法**：**串行下发 + 每次 grep 核验落盘**。

**验证**：核验清单（逐项 grep 计数）。

同轮另一个事故：**在 `Edit` 的 `new_string` 里手工写 `\"` 转义，顺序颠倒** ——
导致生成的字符串提前闭合、反斜杠落到字符串外 → `SyntaxError: missing ) after argument list`。
改用**单引号包裹 JS 字符串**（内部双引号无需转义）+ Python 脚本精确替换才解决。

> 相关：**想"在某行后追加"时，`new_string` 必须包含 `old_string`** ——
> 否则等于把那行删掉（v0.7.0 实测误删过一行 NAMES 映射）。

## 坑 13：一个参数是怎么"死掉"的（两条并行链路，后者静默覆盖前者）

**现象**：用户报「影响范围是不是没用了」。实测证实 —— 而且比报告的更严重：
有边缘点时，点位「影响范围」= 1/9/30 与控制器「影响范围倍率%」= 0/100/500，
**整行 40 根柱子的高度序列完全相同**。

**根因**：`resolvePoints` / `buildExprCore` 里先算出 `rSym`（根数 × 倍率换算的半径），
紧随其后被边缘点距离**直接覆盖** —— 赋值了但不参与结果。这种"死参数"不会有任何报错，
唯一的暴露途径是用户发现"改了没反应"。

**修法**：v1.0.0 宽度收敛为**单一真相** —— 只由左右边缘点决定，删掉三个失效/隐藏参数，
面板加「均分边缘点」按钮替代"填数字设宽度"。

**教训**：新增一种控制方式时，必须同时决定**旧方式的命运**（删除 / 显式降级 / 明确优先级）。
留两条并行链路 + 静默覆盖 = 必然产生死参数。

**实测方法**（可复用）：改变被测参数，比对**整行输出序列**是否逐点相同；
再补一个对照组（删掉边缘点后参数恢复作用）证明是"被覆盖"而不是"公式算错"。

## 坑 14：Shotgun Surgery 的实锤与参数表

**量化**：审计时统计 12 个参数 × 8 个站点（默认值表/预设键/读面板/存预设/填面板/建UI/表达式读取/onChange），
加一个参数平均要改 **5~7 处**。这是 Fowler《重构》里的 **Shotgun Surgery**（Change Preventers 类）：
"一个逻辑变更被迫散改多处"，漏改的表现就是"某个控件改了没反应"。

**修法**：`PARAM_SPECS` 参数表 —— 每个参数只声明一次
`{ key, label, ui, kind, def, lo, hi, mode, group }`，
`DEFAULTS` / `PRESET_KEYS` / 建控件 / 读面板 / 存预设 / 填预设 / onChange 推送 **全部由它派生**。
加参数 = 表里加一行 + UI_ROWS 挑个位置。

**附带收益**：「面板→参数」与「面板→预设」合并为同一条路径（readParams 复用 collectParams），
参数读写路径 6 条 → 5 条，且钳制口径不可能再分叉。

## 坑 15：审计工具本身也会骗人（两个教训）

**① 静态分析器**：第一版花括号配对没剥离字符串字面量，`str.charAt(0) !== "{"` 里的 `{`
被计入深度，把 21 行的 `jsonParseSlots` 报成 1312 行。
⇒ **审计脚本产出的数字也要反向校验**（拿已知长度的函数对一遍）。

**② 探针选择**：验证"负基础高度分叉"时第一版挑了**峰顶那根柱子**，5 组全部"一致"——
因为峰顶恒等于峰高，与基础高度无关，根本测不到差异。换成窗口内/外的柱子立刻暴露 10/30 组分叉。
这与之前"用最高柱验宽度"是同一个毛病：**先想清楚这个差异会体现在哪条契约上，再选观测点**。

**反向对照**：源码级体检断言（"不许出现 X 写法"）必须做反向对照 —— 喂入回归代码，
断言必须变红。本仓库已有先例：`var a = 1, b = 2;` 这种更常见的写法，第一版正则抓不到。
