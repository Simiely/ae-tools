## v0.9.0(2026-09-18)— 高度公式变更:衰减作用在「基础高度之上」的区间

- **真机问题**:用户报「左右控制了之后只是影响范围,但是无法让最低的上去,必须要高度足够高,这样的可控度还不够太够」
  —— 期望「可控范围内的竖条都会起效果,只是影响由于距离相对较小」
- **根因(已量化)**:旧公式 `柱高 = max(峰高 × 衰减, 基础高度)`,要看见窗口边缘必须
  **`峰高 > 基础高度 ÷ e`**(默认 e=30% 时是基础高度的 **3.33 倍**)。
  基础高度一高,边缘贡献就被地板钳平,**与范围外毫无差别**。
  实测:峰高 237.6 / 地板 150 → 边缘贡献 71.3,被钳到 150
- **修复**:`柱高 = 基础高度 + (峰高 − 基础高度) × 衰减`
  - `pointContribution` 加 `baseH` 参数,返回「**超出地板多少**」而非绝对高度
  - `combineHeights` 从 `max(合成, 地板)` 改成 `地板 + 合成`
  - 表达式同步:`eff = pk - baseH; if (eff > 0) { v = eff * f; }` + 收尾 `h = baseH + h;`
  - `baseH` 未给或为 0 -> `effH = peak`,**与旧公式逐点相同**(旧调用零改动)
  - 默认「边缘高度%」30% -> **10%**(新公式下 10% 已足够可见,边界台阶也只有约 10% 可用高度)
  - ⚠️ 两个改动**必须成对**:只降默认值不改公式反而更糟(门槛从 3.33 倍涨到 10 倍)
- **连带修复**:`countVisibleBars` 旧版给下层传 `baseH=0` 再自己判 `h > baseH`,那是在躲
  `combineHeights` 的 max 钳制;新公式下传 0 会让贡献退化成「从零起算」,边缘又被判不可见
  (实测可见根数 9 -> 7)。已改成把 `baseH` 真实传下去
- **副作用(如实说明)**:范围边界会出现一道台阶 = `可用高度 × e`,这是「圈定范围」契约的固有代价,
  由「边缘高度%」控制大小(e=0 时无台阶但边缘恰好落在地板上)
- 实测 7 组 (峰高,地板) 组合:**全部边缘可见且峰顶精确 = 峰高**
- 测试 1102 -> **1131 断言**(+29);含 4 条表达式等价性 + 7 组跨地板组合契约;反向对照 6/6 会变红
- 语法 ✓ BOM ✓ 已部署逐字节校验 ✓

## v0.6.0(2026-09-18)— 「边缘高度%」做成可调参数(取代写死的常数)

- **新需求**:用户要「你还是做成一个可控制的参数」
- 把 v0.4.1 写死的 `FALL_EDGE = 0.65` 换成控制器滑块,并改用**标准窗口族**的构造方式:
  `w(x) = e + (1 − e) × falloff(x, 曲线类型)`,`e = 边缘高度% / 100`
- **依据**:这就是 **Hamming 窗的一般化** —— Hamming 定义为 `0.54 − 0.46cos = 0.08 + 0.92 × Hann`,
  即「常数底 + 原曲线的缩放版」
- 语义(可直接操作):e = **窗口最边缘那根柱子保留峰高的百分比**
  - 100% -> `w ≡ 1` = 矩形窗(Boxcar):窗口内每根都满高、边缘硬切、根数最准
  - 0% -> `w = falloff` = 纯 von Hann:山形最柔,但边缘归零 ⇒ 看不见
  - 30% -> 默认
- ⚠️ 这是**此消彼长**:边缘调高 -> 根数准但边缘硬;调低 -> 山形柔但边缘矮。
  Harris 1978 讲的就是这个权衡,不存在"同时最优"
- ⚠️ 滑块是**生成时**写进控制器的 —— 已有工程要重新点「生成 / 重建」才有;
  表达式对该滑块缺失做了 try/catch 回退(取默认值),所以旧工程不会报错
- 实测「窗口内最低/最高」恰好等于设定值(30% -> 30%),参数语义与显示结果完全对得上
- 测试 931 -> **952 断言**(+21)
- 语法 ✓ BOM ✓ 已部署逐字节校验 ✓

## v0.5.0(2026-09-18)— 算法升级:kNN 半径 + 检索权威定义确认窗函数归属

- **来源**:用户要求「有别的算法吗,检索一下网络」,并强调「任何尝试都要以搜索到的可信度高的内容为前提」
- **检索结论一(改变了实现)**:我们那条曲线有名字 —— 它是 **von Hann(升余弦)**,两端**数学上必然归零**
  - MathWorks `tukeywin` 文档原文:「The Tukey window is a rectangular window with the first and last
    r/2 percent of the samples equal to parts of a cosine… If you specify **r ≥ 1, an L-point
    von Hann window is returned**」
  - SciPy `signal.windows.tukey` 文档原文:alpha = 「the fraction of the window inside the cosine
    tapered region. If zero → **rectangular window**. If one → **Hann window**」(引 Harris, F.J. 1978)
  - ⇒ 边缘柱子看不见**不是参数没调好,是窗函数选错了**;所有平滑窗的两端都趋近 0,这是数学性质
- **检索结论二(更关键)**:旧半径公式 `(m+1)/2 × 柱距` 是「半个柱距的估算」,根数必然在 m/m+1 之间漂。
  正规做法是取「**第 m 近那根柱子的实际距离**」—— KDE 里的 **k 近邻 / 自适应带宽核**:
  `m 奇 -> (m-1)/2 + Δ`;`m 偶 -> m/2 - Δ`;判定改成**非严格 `≤`**
- **实测**:旧算法 填 1/3/7/9/15 -> 得到 2/4/8/10/16;新算法 -> **1/3/7/9/15 每一档都恰好**
- **踩坑**:kNN 半径末尾**必须乘 `(1 + 1e-9)`** —— `k×柱距` 常算出 `150.49999999999997`,
  而"第 m 近"那根恰好落在 `150.5`,不放大就会把它挤掉(实测填 9 只得 8 根)
- 唯一退化(几何事实):点位正落在**两根正中**且 m 为**奇数**时,两侧等距无法二选一 -> 得 m+1 根
- 测试 908 -> **931 断言**(+23);反向对照验证旧公式必然变红
- 语法 ✓ BOM ✓ 已部署逐字节校验 ✓

## v0.1.2(2026-09-17)— 修复拖动形状图层无法移动整行

- **真机问题**:用户报「现在拖动集合图层,无法移动呢」
- **根因(我的设计错)**:位置表达式里写了 `bx - transform.position[0]`,而 `bx` 又是从**控制器**的
  合成坐标推出来的 —— 两边一减,**图层自身的位置被完全抵消掉**:
  `合成X = 图层X + (bx − 图层X) = bx` ⇒ 与图层位置完全无关。
  我当时把"行锚定在控制器上"当成设计特性,但这违背 AE 用户的直觉:**形状图层拖不动就是坏了**
- **修复**:**形状图层自己就是锚点** —— `bx = transform.position[0] + …`、
  `pk = transform.position[1] - pp[1]`、位置表达式输出**纯偏移量** `[(i-(N-1)/2)*(W+G), -h/2]`。
  生成时把形状图层 position 显式设为 `[合成宽/2, 合成高×基线比]`
- **测试当场抓到漏改的第三处**:`pk = cp[1] - pp[1]` 还在引用已删除的 `cp`(直接 ReferenceError)
- 新增第四节专门盯这个 bug:位置输出与图层位置**无关**(可拖动的前提)、图层右移 200 -> 合成坐标同步右移 200、
  几何不变量(底边在合成坐标里恒等于图层 Y)
- 测试 486 -> **621 断言**(+135)
