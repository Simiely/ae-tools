# 更新日志 · 山峰频谱 MountainSpectrum

## v1.5.7 (2026-09-21) —— 「山峰 柱」可设父级跟随运动（基准改挂控制器）

- **需求原文**：「我希望山峰 柱可以选择一个父级，跟随运动，但是这样的话，之前到山峰的效果就没有了」
  → 补充说明：「我就是希望控制点的位置不变。也能有效果」
- **现象**：给「山峰 柱」设父级（想让整座山跟随运动）后，山峰形状整个散掉。
- **根因（坐标系混用，不是父级功能本身的问题）**：表达式的高度计算要拿「整行基准 X/Y」与
  「峰点坐标」相减，而基准原先取自**本图层自身的 `transform.position`** ——
  在 AE 里给图层设父级时 AE 会**补偿**该值（改写它以保持视觉位置），基准随之漂移；
  峰点没有父级（仍是合成坐标）→ 两者差一个父级偏移 → 距离算出错值 → 形状散掉。
  **实测（40 根取样）**：只有柱的坐标系平移 → **33/40 根高度改变**；全部图层一起平移 → 0/40 改变。
- **修法**：基准改用**「山峰 控制器」的位置**（`c.transform.position`）—— 它是空对象、
  不该跟随运动，于是基准与峰点恒处在同一坐标系 → **形状由控制点唯一决定**，
  而「山峰 柱」可自由设父级让整座山跟随运动。
  - 改动 4 处：基准 X（`bx`）、总闸基线 Y（`hMax`）、峰高基线 Y（`pk2` / `pk`）
  - **等价性**：`generate()` 里控制器与「山峰 柱」同置 `[centerX, baseY]`，
    故对现有用法**无行为变化**（除非你曾手动把控制器拖到别处）
- **副作用（属修正）**：拖动「山峰 柱」图层现在**只平移整行、不再改变山形** ——
  这正是本文件一贯的设计意图（「拖动形状图层移动整行」），此前因基准取自图层自身而实际会连带变形。
  **山形从此只由控制点决定**，符合直觉。
- 断言 273 → **284**。新增**第十三节**「柱图层设父级 / 拖动不再影响形状」：
  ① 柱位置平移（±300 / −500）→ 40 根高度**逐位不变**；
  ② 控制器平移 → 形状**必须改变**（证明基准确实换了源，否则断言可能是假绿）；
  ③ 柱的 Y 变化不影响形状、控制器 Y 变化影响形状。**已做反向对照**。
- 顺带修一条**漏网的弱断言**：`核心用图层自身 X 定位柱子` 用的是
  `indexOf("transform.position[0] + …")` —— 把基准改成 `c.transform.position[0] + …` 之后
  **它照样通过**（`c.` 之后的子串仍匹配）。已改为带 `c.` 前缀的完整串。
- ⚠️ **已有工程需重新生成一次**才会用上新表达式（表达式是生成时写进图层的）。
  因为控制器与柱同位置，重新生成后形状与原来一致。

## v1.5.6 (2026-09-21) —— 修「起伏曲线」枚举越界分叉（架构审计发现）

- **来源**：2026-09-21 架构审计的**边界分叉探测**（1000 次逐根比对）发现，**不是用户报告**
- **现象**：`ftype`（起伏曲线）取非法枚举值时，纯函数与表达式结论不同 ——
  纯函数 `falloff` 用 `=== 1/2/3` 精确匹配，越界落「默认分支 = 余弦」；
  表达式用 `< 0.5 / < 1.5 / < 2.5` 阈值分段，越界落「else = 二次」。实测 `ftype = 9` 时 **40 根里 8 根不一致**。
- **触发路径真实**：面板下拉框只能给 0~3，但控制器上的「起伏曲线」是 **AE 原生数值滑块，能拖出范围** ——
  一出界，画面按二次曲线渲染、状态栏回报的可见根数却按余弦算，**数字与画面对不上**。
- **修法**：两侧统一「先 `Math.round` 再夹到 [0,3]，越界 / NaN 回退 0（余弦 = 面板默认值）」。
  新增纯函数 `normalizeFalloffType()` 并导出；表达式内联同一规则（读 `ftype` 后立即夹紧为 `ftp`）。
- **⚠️ 唯一行为变化**：`ftype ∈ [3.5, +∞)` 从「二次」变为「余弦」（非法值回退默认）。
- **测试**：266 → **272**。新增**第十二节「边界值等价性」**，把审计探测的 **25 个边界用例 × 40 根 = 1000 次
  逐根比对**固化进断言 —— 以后任一侧改动都会在这里变红。
  **反向对照已验证**：两侧同时回滚立刻报出「ftype = 9 柱8 纯=55.78 式=40.8」。
- **配套**：新增仓库级验收脚本 `verify.py`（见根 CHANGELOG）。

## v1.5.0 (2026-09-20) —— 边缘羽化带(空间线性过渡, 取代时间帧缓冲)

**需求原文**:「现在的方式似乎没有缓冲 3 帧。可能 3 帧缓冲这个命题不太成立。改成控制边缘那个位置的范围。之前是一个点，现在是把点扩展为一个宽度的范围，在这个范围内，线性变化。是不是更好实现。」

### 为什么时间缓冲不成立（检索结论）

v1.4.0 的帧缓冲只对"点位有关键帧动画"有意义——静态合成里 fOut 每帧恒定，表达式输出不变，
用户看到的跳变是**相邻两根柱之间的空间高度差**，时间维度上根本没有过渡过程可插值。
检索佐证：这类"窗口硬边界突变"的标准解法就是 feathering（WaveLab/SpectraLayers 选区羽化、
FFT 的 Hann 窗函数）——把硬边界换成一段斜坡，与本插件场景完全同构。

### 改动

- 新参数**「边缘过渡(根)」**（默认 3，0 = 硬边界）取代「节奏缓冲帧」：边缘点从"一个点"
  扩展为"点 + 羽化带"，带宽 = N 根柱距，随各点半径换算
- **普通柱**：衰减窗口扩展进羽化带，山脚从 baseH + effH×edge 线性收到 baseH
  ——顺带消除了「边缘高度%」>0 时边界处的固有跳变
- **节奏条**：山内核心(liftC>0)跟随轮廓；带内 = 独自地板 + (边界轮廓值 − 独自地板) × (1−s)；
  带外独自高 —— 相邻柱高度差被带宽摊薄，无跳变
- 纯函数 `pointContribution`（加 fw/pitch 形参）/ 新增 `pointBand` / `barHeightAt` 与表达式严格镜像；
  等价性测试新增 fw=3 用例组；测试 242 → **249** 全绿
- v1.4.0 的时间帧缓冲代码已全部移除（参数槽位由「边缘过渡(根)」接管，预设槽位自动迁移）
- **热修**：v1.5.0 首发漏改 UI_ROWS 布局（残留 "rhyBuf"）→ 「边缘过渡(根)」控件未创建，
  「应用预设」回填时 `U[sp.ui]` 为 undefined 报 TypeError。已修 + 新增回归测试
  「参数表 UI 覆盖」防止任何参数控件漏建（250 断言）
- **健壮性加固**：`applyParamsToUI` 逐控件守卫 —— 单个控件缺失只跳过该参数，
  不再让整个「应用预设」崩掉；新增「应用预设全链路」回归测试（收集 → 槽位 JSON →
  解析 → 回填 → 再收集 逐字段一致）与「旧版含 rhyBuf 键的 JSON 导入」兼容性测试（252 断言）

## v1.3.0 (2026-09-20) —— 节奏条平滑化(取大压缩)

**需求原文**:「波峰不平滑，变高的范围内的需要压缩高度，让它看起来就是平滑的。就像没有格外高度做出来的那种效果。」

### 根因

v1.1.0 的结合公式是「固定增量」：柱高 = 节奏地板 + 山丘抬升。山内节奏条永远比邻居高出
`baseH × (高度% − 100)`（默认 40×0.8 = 32px），山一高它就跟着高，锯齿感同步放大 —— 山内轮廓
始终不是纯山丘。

### 改动（用户截图②为参照：山内不应有额外高的柱）

- 结合公式改为【取大压缩】：**柱高 = max(普通柱高度 baseH+抬升, 节奏地板)**
  - 山内：普通柱 > 地板 → 节奏条与邻居同高，轮廓 = 纯山丘，无锯齿
  - 山外：抬升 = 0 → 节奏条 = baseH × 高度%，独自高不变
  - 山脚过渡带：max 连续，无跳变
- 纯函数 `barHeightAt` 与表达式模板**两处严格镜像**（等价性测试用真表达式 + mock 逐点比对）
- floor 不高于普通柱地板时（异常/旧预设）退回旧「固定增量」口径，向后兼容
- 测试：核心不变量改为 `h_开(i) = max(h_关(i), 地板_i)` 逐根验证；新增「山内节奏柱被吞掉」

## v1.1.0 (2026-09-18) —— 节奏条(每 N 根一根更高)

**需求原文**:「增加一个开关控制，打开之后，可以选择每几个竖线有一个更高的竖线。那么因为有了一个更高的竖线了，进入到放大区域的时候，需要有办法让它像普通竖线一样放大，就还是保证那个流线型。出去的时候又恢复到它独自高一些。」

### 新增

- **节奏条开关**(默认 0=关): 关闭时逐点等于 v1.0.0 的公式 —— 旧行为零变化
- **节奏间隔**(默认 8): 每 8 根竖线第 1 根是节奏条(锚定 `i % 间隔 === 0`, 从最左开始, 改数量/间距图案不变)
- **节奏条高度%**(默认 180): 节奏条独自高度 = 基础高度 × 180%

### 山丘结合公式(先调研后定案)

采用**固定增量**形态: `柱高 = 节奏地板_i + 山丘抬升量`(普通柱地板 = baseH, 节奏条地板 = baseH × 高度%)。

| 区域 | 普通柱 | 节奏条 | 性质 |
|---|---|---|---|
| 山外 | baseH | baseH × 高度% | 节奏条"独自高一些" |
| 山内 | baseH + 抬升 | 节奏地板 + **同一个**抬升 | 全场同量放大, 轮廓连续无跳变 |
| 山顶 | 峰高 | 峰高 + (高度%−100%)×基础高度 | 只比峰高出固定增量, **不会成倍戳出** |

调研依据: 该结构即调幅(AM)的两种形态取舍 —— "图案×增益"(s(t)=[1+k·m(t)]·c(t), CUHK ELEG2310 讲义)
会让节奏条在山顶成倍戳出包络(×1.8), 破坏流线型; "包络+固定偏移"才是用户要的"保持流线型"
(ScienceDirect《Digital Signal Processing》Ch.10: 相加只会平移图案, 不改变包络形状)。

### 实现

- `barFloor(i, rhy, baseH)` 纯函数 + 表达式内核严格镜像(`fl` 收尾); 表达式对 3 个滑块缺失
  try/catch 回退"关" —— **旧工程(无这些滑块)行为与 v1.0.0 完全一致**
- 3 个参数走 `PARAM_SPECS(mode:"ctrl")`: 面板新增「节奏」分组(实时生效, 无需重新生成)、
  控制器自动建滑块、预设自动携带(旧预设文件缺这 3 键按默认"关"处理, 双向兼容)
- 总闸交互: 节奏地板不参与总闸缩放(山外节奏条高度不受「山峰 总高度闸」影响); 山内随抬升量一起缩放

### 测试

192 → **225 项断言全过**(第十一节 33 项; 含 2000 次逐根数值比对)。核心不变量:
**开关只改地板, 不改山丘抬升量**(40 根逐根验证) —— 这就是"像普通竖线一样放大 + 流线型"的数学表达。



依据 `MountainSpectrum-架构审计报告.md`（对 v0.9.0 全代码审计，含可复跑实测）逐条落地。

### 删除：两个死参数 + 一个隐藏开关

| 删除项 | 实测证据 |
|---|---|
| 点位「影响范围」滑块 | 有边缘点时，`影响范围 = 1 / 9 / 30` → 40 根柱子的高度序列**完全相同** |
| 控制器「影响范围倍率%」 | `倍率 = 0 / 100 / 500` → 也**完全相同**（且面板无入口、提示不提，更隐蔽） |
| 点位「边缘控制」滑块 | 它只是"跳过边缘点查找"的性能开关，宽度收敛后已无意义；且从未在面板上出现过 |

## v0.9.0 (2026-09-18) —— 高度公式改为「衰减作用在地板之上」

- 用户报：「左右控制了之后只是影响范围，但是无法让最低的上去，必须要高度足够高」。
- 旧公式 `柱高 = max(峰高 × 衰减, 基础高度)`：要看见窗口边缘必须 `峰高 > 基础高度 ÷ 边缘高度%`，默认 30% 时是基础高度的 **3.33 倍**（实测峰高 237.6 + 地板 150 → 边缘被钳到 150，与范围外毫无差别）。
- 新公式 `柱高 = 基础高度 + (峰高 − 基础高度) × 衰减`：衰减作用在**地板之上**的区间，只要 `边缘高度% > 0`，窗口内每一根都保证高于地板；**峰顶仍精确等于峰高**。
- 「边缘高度%」默认值 30% → **10%**（新公式下 10% 已足够可见，且范围边界的台阶只有约 10% 可用高度）。
- ⚠️ 副作用（如实说）：范围边界会出现一道台阶 `= 可用高度 × 边缘高度%`。这是"圈定范围"的固有代价，不是缺陷。
- ⚠️ `countVisibleBars` 必须把 `baseH` 真实传下去 —— 旧版传 0 再自己判定是在躲 `combineHeights` 的 max 钳制；新公式下传 0 会让贡献退化成"从零起算"，边缘又被判成不可见（实测可见根数 9 → 7）。
- 断言 1102 → 1131。

## v0.6.0 (2026-09-18) —— 「边缘高度%」参数化

- 把 v0.4.1 写死的 `FALL_EDGE = 0.65` 换成滑块，改用标准窗口族的构造：`w(x) = e + (1 − e) × falloff(x)`。

- ⚠️ 此消彼长：边缘调高 → 根数准但边缘硬；调低 → 山形柔但边缘矮（Harris 1978 讲的权衡，不存在同时最优）。

## v0.5.0 (2026-09-18) —— 检索权威文献后的算法升级

- **结论一**：我们的起伏曲线 = **von Hann 窗**，两端**恰好为 0** ⇒ 窗口边缘必然看不见（MathWorks `tukeywin`、SciPy `signal.windows.tukey` 文档；引 Harris 1978）。所有平滑窗两端都趋近 0，这是数学性质，无解 ⇒ 只能把曲线整体抬起来（Hamming 构造）。
- **结论二**：半径公式 `(m+1)/2 × 柱距` 是"半个柱距"的**估算**，导致根数在 m / m+1 之间漂。改为取**第 m 近那根柱子的实际距离**（kNN / 自适应带宽核），判定改成非严格 `≤` ⇒ 填 m 恰好 m 根。
- ⚠️ 半径末尾必须乘 `(1 + 1e-9)`：`k×柱距` 常算出 `150.49999999999997` 而边界柱恰在 `150.5`，不放大就会漏掉那根（实测填 9 只得到 8 根）。
- 断言 908 → 931。
